A++++ Engineering Plan — Six Pillars

Progress: 0 / 6 pillars complete — foundational quality work in progress across build hygiene and test discipline
Goal: take the project from a working but fragile B/B+ state to an A++++ standard where a senior engineer can clone the repo, run one command, get a green build, pass the test suite, and never fight leaked artifacts, undocumented assumptions, or brittle runtime behavior.

Pillar 1 — Clean, reproducible build

Why it comes first: without a clean build, CI cannot be trusted, refactors become dangerous, and repo hygiene collapses under artifact drift.
  • ☑ Remove tracked artifact trees from version control and keep them ignored.
  • ☑ Move large runtime dumps and generated logs out of tracked workspace paths.
  • ☑ Consolidate the build flow through one script with explicit modes: build, run, test, package, and full rebuild.
  • ☐ Enforce a single warning policy for project sources through Directory.Build.props.
  • ☐ Keep third-party dependencies on a separate warning policy to avoid vendored-library noise.
  • ☐ Move outputs to a single out/ directory and block repo-root artifact writes.
Done when: a clean checkout plus one build command yields a green build and a clean git status.

Pillar 2 — Test coverage for the real logic

Why this is the highest leverage move: the project’s deterministic logic is exactly where a test gate pays off the fastest: math, decode paths, parser safety, and world-state validation.
  • ☑ Add a dedicated test project without DMA or game-runtime dependencies.
  • ☑ Build a memory-read seam so the FName decode path can be exercised with a synthetic memory image.
  • ☑ Cover the most valuable logic areas:
    • vector and matrix math
    • bone transforms and aim-smoothing math
    • JSON parsing and fuzz safety
    • SteamDecrypt and FName decode
  • ☐ Add synthetic raycast and world-projection cases for visibility logic.
  • ☐ Add coverage measurement and a minimum threshold for pure logic.
  • ☑ Make the test runner part of the project build flow.
Done when: the test command is required for green builds and pure-logic coverage hits a meaningful target.

Pillar 3 — CI as enforcement, not decoration

Why this matters: the overlay cannot run in CI, but the project can still enforce compile correctness, tests, and hygiene using a Windows runner.
  • ☐ Add a GitHub Actions Windows pipeline for release build and test execution.
  • ☐ Fail on any nonzero exit from the test binary.
  • ☐ Fail if git status is dirty after build/test.
  • ☐ Add a static analysis pass with a staged warning gate.
  • ☐ Publish build, test, and hygiene badges in the README.
Done when: every push or pull request shows a clear green compile-and-test signal.

Pillar 4 — Defensive coding and crash hygiene

Why: the project already includes a crash handler and session logs, which is a strong foundation. What is missing is systematic hardening and reliable diagnostics.
  • ☐ Wrap timer setup in RAII so every Begin has a matching End.
  • ☐ Centralize memory reads behind a checked interface that validates bounds and alignment.
  • ☐ Add bounded retry/backoff logic for hardware and serial communication paths.
  • ☐ Extend crash handling to create dump artifacts and structured failure logs.
  • ☐ Turn on stricter security and bounds checks where the compiler can help.
Done when: fuzzed parser input cannot crash the app, and a crash leaves a readable dump and log behind.

Pillar 5 — Architecture clarity

Why: the project has grown through multiple passes and feature-specific additions; it now needs a single documented operating model instead of implicit assumptions.
  • ☐ Write a project architecture note covering the full update path: read → decode → model → render.
  • ☐ Define one explicit entity model and pass ordering for update logic.
  • ☐ Replace the worst global-state patterns with explicit runtime containers.
  • ☐ Refactor in small, build-safe stages rather than one risky rewrite.
Done when: a new engineer can trace one entity from memory read to render without hunting through unrelated modules.

Pillar 6 — Documentation and process discipline

Why: a project this complex is only safe if the process is as clear as the code. Strong documentation culture is already present; the work is to formalize it.
  • ☐ Add a README with purpose, one-command build, and test flow.
  • ☐ Add a changelog and conventional commit guidance.
  • ☐ Enforce a pre-commit checklist: clean status, pass tests, no tracked artifacts.
  • ☐ Keep plans in docs/ and archive completed work so the project history stays readable.
Done when: a stranger can clone the repo, read the docs, build it, and pass the tests without tribal knowledge.

Definition of A++++

  • ☐ One-command build works from a clean checkout.
  • ☐ git status stays clean after build and test.
  • ☐ Test suite is required for green status.
  • ☐ Line coverage clears a meaningful threshold on pure logic.
  • ☐ CI enforces compile, tests, and hygiene.
  • ☐ Runtime errors are logged and dumps are created when needed.
  • ☐ Docs explain the architecture and the operating model.
  • ☐ Repeated builds are deterministic and never leak artifacts into the repo.
